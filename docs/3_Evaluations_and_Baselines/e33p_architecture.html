E33p: the notes point, the reading layer opens the exact tokens behind them

E33n showed that at 30M nearly all the value of distant text on long documents is exact copying, and a note (a summary of about 8 tokens) cannot return an exact token. E33p keeps the same notebook but changes its job: the notes become an index. Each block of queries uses the notes to find where to look, then reads the raw, uncompressed tokens behind its best notes. This page lays out the design as I understood it from the spec, so you can check it before any code is written.

1 · Why: what E33n found (16k-token documents, positions 2k–16k)

Four 30M models, identical except for the reading layer, were scored on held-out long documents (64 rows per source, 156 documents). The number is the loss: the model's average surprise at the true next token, in nats. Lower is better.

G is the far-context gap: how much better the dense ceiling (which may re-read every earlier token) is than the window control (which sees only the last 512 tokens). G = 0.1335 nats per token, so the dense model gives the right token about 14 % more probability on average. An arm's share of G is how much of that gap it closes; higher is better. Both notebook models closed about 6 %, far below E33n's own 15 % stop line.

Where G sits: the copy split

Each scored token is a far copy if the same 4 tokens (3 of context and itself) appeared earlier only beyond the 512-token window, a near copy if they appeared inside it, and no copy otherwise.

Read it as: one token in ten is a far copy, and on those the dense model is 1.361 nats better, meaning it gives the right token about 3.9 times more probability. That is almost all of G. The notes close only 2 % of it. On tokens that are not copies the gap is tiny (0.007 nats), and there the notes close nearly all of it. So the 30M model can copy (the dense model does), and the notebook helps with gist; what the notebook cannot do is hand back an exact earlier token. With a stricter 8-token test the picture holds: 5.2 % of tokens, 63 % of G, notes close about 1 %.

3 · A worked toy example: why the exact token becomes copyable

A 31-token text whose last token, “ship”, should be followed by “Kestrel”, a word last seen 25 tokens earlier, beyond the window. The model has to copy it. Toy scale: pages of 8 tokens (real 256), 2 notes per page (real 32), a window of 8 tokens (real 512), a block of the last 4 queries (real 128), 2 notes chosen per block (real 64), and pages-open opens 1 page (real 2). No page overlap here; section 4 shows it. illustrative All scores and weights are hand-built to show the mechanism. They are not measured.

    raw token (window, or any earlier token for the dense ceiling) note (gist) opened token

    “Share of ‘Kestrel’ in what the read returns” counts the weight on the exact token plus, for a note, its weight times the part of the note that is “Kestrel”. For that part I assume a note's value is the assignment-weighted average of its tokens (note 1a: 22 % “Kestrel”). The real writer learns its own value, so this is an upper picture, not a measurement. The toy has only 30 earlier tokens, so the dense ceiling faces few distractors; at 16k it faces thousands.

    One consequence the spec does not address: a chosen note whose members all sit inside the query's window opens nothing, yet it used one of the 64 places.     7 · Where the spec was open and I had to choose

    1. Which assignment A[t, n]. The writer has 8 heads and 2 rounds; each head has its own softmax over notes. I take the last round, averaged over the 8 heads (the code already averages heads this way for a note's position).
    2. One choice per block for all 9 query heads. There is one key/value head, so one opened set per block, scored with the 9 heads' votes added. The alternative is 9 sets per block.
    3. κ and the choice are redone in every loop round. The reading layer's raw keys change each round, so κ does too. The notes' values are written once.
    4. Votes only from queries that may see the note. Each query's softmax runs over the notes closed for it. A note that closes mid-block gets votes only from the later queries.
    5. Notes whose members all sit inside the window still compete for the 64 places, as written; they then open nothing. Should the choice skip them? (question)
    6. “About 512 opened tokens” is an average, not a cap. m = 64 notes is fixed; the token count varies. Should there be a hard cap for the kernel? (question)
    7. Note size. The spec calls a note “a 576-number average”. In the code a note enters the read as one 64-number key and one 64-number value (one key/value head of width 64), made from a 512-number writer state. The page uses those numbers.
    8. Pages-open differs only in what it opens. It keeps the gist notes keyed by κ, scores pages with the same votes, and opens each shared token once where its two pages overlap.
    9. The writer's own note key goes unused in the tied arms. κ keys both the choice and the gist entries; the spec's “writer” option for the note key would use the writer's key for both.
