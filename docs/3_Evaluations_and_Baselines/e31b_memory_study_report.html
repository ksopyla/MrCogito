Two memories, long books: what each one can really do

We trained two designs of long-range memory the same way, gave them the same exams, and tested them on books from 1,000 up to 128,000 tokens. This page shows what the exams look like, what each memory can and cannot do, and what it costs.

The short answer

Think of a student reading a very long book for an exam. The student cannot reread the book, only a notebook of short summaries written while reading. Both designs are ways of writing that notebook. A good notebook lets the student answer questions about page 3 while sitting on page 100,000.

The two designs

Both split the book into overlapping pages of 256 tokens and write a small set of notes per page. The question at the end can only see the notes, never the book, so the notebook is the only way to answer. The difference is how the notes are written.

What we fixed first

Both designs originally stamped each note with its absolute page number. Trained on 2k books, they looked for facts at "page positions" that do not exist in a 128k book, and fell to chance by 16k. We re-anchored every note to the question instead ("this note is before you"), which made both designs work on longer books. For E30 this change alone lifted it on 32k books from guessing to 62%.

How much can one note hold?

The key question for a million-token memory: how many tokens can one note summarise before facts get lost? Each dot is one training run (seed), on a 1k book. More tokens per note means a smaller, cheaper notebook.

Why 48 tokens per note failed

We tested four explanations. Giving each note 8 read-out slots instead of 1 did not help (30%), and neither did a longer 512-token page (29%). Making each note twice as wide (1024 numbers instead of 512) lifted it from 25% to 84%. The note simply could not hold enough.

How E30's ratio was chosen

An earlier sweep (22 September) tried 3, 6 and 11 tokens per note; 11 failed, so 6 became the default. That sweep also changed the page length at the same time, so we measured it again here. E30 handles single facts at 12–24 tokens, but never learns to hold 8 facts from scratch at any ratio.

What it costs

Time to read one book on one RTX 3090, as the book grows. Both axes double at each step. Every memory grows linearly (twice the book, twice the time); dense grows about 3.4× per doubling.

Where the time goes at 128k

Extra time on top of a model with no memory, split into the note writer and everything else. E31's own encoder is the structural cost; the notebook size was a setting (5 notes per summary) that costs nothing to fix.

A million tokens does not fit on one 24 GB card for any design yet: the main model's working memory (not the notebook) needs about 14 GB at 512k. Reading the book in chunks and keeping only the notes will fix that for both.

Reasoning: one look is not enough

To follow a chain hidden among decoy chains, the model must look up step 1, then use the answer to look up step 2, and so on. We tried letting the question look at the notebook 4 times instead of once, and in a second version we also trained each look to find the right step. Neither helped.

First-letter accuracy at 1k, chance 25%. "Short names" = chain nodes of 8 letters instead of 32, so each node fits in one note. Across ten comparisons the gain from 4 looks was between −2 and +6 points: noise.

A measuring trap we fell into

We first scored every letter of the answer while showing the model the correct letters before it. When the book contains several candidate answers (several facts, decoys, chain nodes), two correct letters already say which candidate is meant, and the model can copy the rest. That inflates the score. The honest measure is the first letter, which the model must produce with no hints.

This overturned one early claim: E31 does not follow the 4-step chain with question-anchored notes (53%, not 96%). With the order code it does, on the honest measure. All numbers on this page are first-letter scores.

What this means, and what comes next

  1. Build E32, the two-level memory. Detailed notes (one per 6 tokens) plus a coarse index on top (one wide note per ~48 tokens). The question checks the index first, then reads only the relevant pages. Use E31-style notes with one note per summary and an order code.
  2. Solve content and order together. The order code costs single-fact lookup (47–98% at 128k depending on seed, against 94%), and our attempt to keep both in one note (half content, half order) did not beat either. Separate channels are the next thing to try.
  3. New reasoning mechanism (E33, second try). Instead of looking at the notebook more times, let the fetched notes exchange information with each other before answering, or let the model write intermediate steps as tokens.
  4. Read in chunks so a million-token book fits on one GPU.

Setup: 30M-parameter models (hidden size 960, 4 layers), identical training for every design, 256-token local window so the notebook is the only long-range path. Length curriculum: 2k, then 8k, then 16k tokens. 64–256 test books per point. Full tables and every run: the E31b study spec in the repository.
