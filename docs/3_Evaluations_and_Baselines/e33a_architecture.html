E33 on text: how information flows through the notebook and the loop

This page follows one document through E33 as it is built and trained today on the text checks. The notebook writer runs first, then the main path, then the read–think loop, the coda layers and the output head. Each stage says what it keeps, what it drops, and what it knows about position. Section 2 explains why the notes cannot tell which of two facts came later. Section 5 maps the 14 Oct results onto the parts. The 2–4 Oct page about the DNA chain test is kept at the bottom as history.

What changed since the 4 Oct version of this page
  • The model that matters now is the 30M text model. It has 8 layers (2 local, the global read, 5 local) at width 576. The old page drew the 4-layer DNA model at width 960.
  • Every token loops. Text has no question boundary, so every token reads the notebook and every token goes through the read–think core 4 times. The old page looped only about 40 question positions.
  • Four coda layers follow the loop, not one answer layer. Rounds 1–3 are decoded through all four, during training only, and their loss is the next token. There are no step targets.
  • The notes carry no position at all: no page number and no rotation. This lets the model read 16k documents after training on 4k ones. It also leaves the model no way to tell which of two notes is newer (section 2).

Width 896, 12 layers: 3 local, the global read, then 1 core layer and 7 coda layers. The writer is still 4.0M (4 %): page width 256, latents 512 wide, notes 64 numbers. Nothing in the writer grows with the model. That ratio is one of the sweep's questions.
Cost of one 4k document
21 pages × 32 = 672 notes, written once. Each token's read covers 256 raw keys plus up to 672 notes (2,720 at 16k). Dense covers up to 4,096 keys. The core runs 4 times over every token, so E33 trains slower than dense: 7.0 h for 1.5B tokens on Odra.

2 · Order: why the notes cannot tell which move came last

The "latest" exam has 5 people. Each starts in a home and moves 10 times, and the moves are interleaved through the story. The question at the end is "Where does Anna live now?", so the answer is Anna's last move. The model has to find Anna's facts and also know which of them came last.

A note carries no position. Its key is not rotated, so the read cannot measure how far back it is. The writer adds no page number, because the page address is switched off. All a latent knows is roughly which part of its page it read. Picture the student's notebook with the pages torn out and shuffled: the notes still say "Anna moved to Kodaford", "Anna moved to Selby", "Anna lived in Borvale", but there is no date or page number to sort them by. The read is a softmax over the notes, which is a weighted average. Shuffle the notes and the average comes out the same.

Document Notes

The positions follow the exam generator: moves are spread over 15–95 % of the document, and Anna's last move sits on average at 88 %. The read weights are illustrative; we have not measured them yet. The measured scores are E33 run 1 on the 8-questions recipe: 95 % at 1k, 22 % at 4k (guessing 20 %), about 5 % beyond 4k. Dense, which keeps every position, learned this task in 2 of 3 runs (77–82 % at 4k).

Why it is built this way

The order was removed on purpose, to make the read work at any length. In the DNA study, notes rotated at their true position stopped working past the training length. Two fixes were built. "Boundary" puts every note at the question position, so it keeps no order either. "Scaled" keeps the order and squeezes the distances into the trained range. Scaled worked: lookup held to 128k, and the in-order 4-hop chain transferred only with it. E33 on DNA used boundary. On text, scaled does not carry over as it is, because it measures distance from one question. On text every token is a reader, so the text version (un-rotated notes) is the boundary idea again. It is why the model reads 16k documents after training on 4k, and why latest fails.

Ways to give the notes an order (proposals, not built)

  • An age signal in the read (recommended). Lower a note's score by a per-head slope × the number of pages since its page closed, the way ALiBi (attention with linear biases) does. Heads with slope 0 keep pure content reads, the others prefer newer notes. ALiBi is known to work beyond the training length. It costs one number per head, added where the read's scores are formed.
  • Slow rotation only. Rotate note keys at their page position using only the low-frequency rotation pairs, which gives a coarse order. This is close to the DNA "mixed" option.
  • Page number in the latent. Switch the page address back on. That gives absolute position, which is likely weak beyond 4k.

3 · Who can see what

Take one reading token. Its local layers see 16 tokens back. Its global read sees the raw keys of the last 256 tokens, plus the notes of every page that closed at or before it. A page that is still open is invisible as notes, but its recent tokens are covered by the raw window. A long page with a short raw window leaves a blind stretch: tokens too old for the raw window, sitting on a page that has not closed yet. The worst case comes just before a page closes. The blind stretch is the page step minus the raw window, when the step is longer.

Geometry

Other rules: a page writes from one document only, so notes never mix documents. Inside the writer, every token of a page sees the whole page, in both directions. That is safe, because a page is read only after it has closed. The local layers and the raw read never cross into another document.

Why it stalled: five causes, none of them in the loop

1
The exam has a guessing floor at about 40 %. The answer is always the target of some link, so "any link target" already scores 44 / 41 / 39 %. A better guess (pick one of the 4 chain ends, 43.75 %) is also open, though no model found it. We read 40 % as "partial reasoning". It is guessing.
2
Nothing in training needed the key. Every chain run started from the single-fact lookup and replayed it during training. With one fact in the book, the question's key is never read. Looking up by key is learned only from that stepping stone: "1 of 8 facts" stays at chance from scratch (dense 27 %) but reaches 95–98 % started from the lookup.
3
The exams share the gap. "Find a fact by its key" plants one fact, and "pick over look-alikes" marks the decoys with a different symbol, so neither needs the key. The in-order chain can be solved by counting blocks: dense can, the memory cannot (its notes carry no order across windows). The first exam that needs the key is "1 of 8 / 16 facts", which is still being calibrated.
4
The pass mark had no measured ceiling. The 75 % gate assumed "three perfect lookups ≈ 94–97 %", taken from the key-free exams. On this exact task, dense reached 44 / 39 %.
5
Too few examples. On chains among distractor chains, transformers first spread their answer over all chain ends, then jump. One study saw the jump after about 400 k examples with single-letter nodes and short contexts (Guo et al. 2025); we gave about 150 k per stage, with 8-letter nodes in 1k–16k books. Without a curriculum each extra hop costs about 10× more data (Yao et al. 2025).
✓
Not a bug. Checked on a tiny model: an exit after pass r equals running r passes; each pass is trained on the right node; every pass and the memory writer get gradient; one pass reproduces the original model exactly. Trained weights: each pass keeps 0.94 of the state, and the per-pass markers are small (0.1–0.25 against a state of ≈ 30). Worth watching, not blocking.

Design verdict (2 Oct), kept as written: yes, it makes sense, and it fixes the two concrete flaws of E33.
  • The answer-forming layers are inside the loop. E33 looped only the global read plus one feed-forward. The layers that turn fetched content into an answer sat outside it, so nothing between two reads could reshape "what I found" into "what I must ask next".
  • "Try to answer" happens through the real head. E33's per-round targets were read through the output head while skipping the two upper layers, so the head was decoding states it was never trained on.
Your design maps onto the best-supported pattern in the literature: an untied first layer, a tied core looped R times, and an untied last layer (Huginn, Mixture-of-Recursions). It is also the classic memory-network hop: the controller state is updated, then the memory is read again (End-to-end Memory Networks, 2015). It uses the same parameters, and with one loop it is exactly today's model.

Old 2 · The layer plan: same four layers, regrouped

Today the main path has four layers: a local layer (16 tokens back), the global read, and two local layers. The loop regroups them without adding any:

  • Prelude, once: the first local layer. It turns the question tokens into a state (it "reads the question").
  • Core, looped 4 times with tied weights: the global read plus the first upper local layer. Each pass is one "read → think" step.
  • Answer layer, untied: the last local layer plus the output head. It formulates the answer after loop 4. During training it also decodes the state after every loop, which is how "try to answer" gets its own loss.

With one loop this is exactly today's network. We can start from the best E31 checkpoint, and lookups can still be answered from loop 1.

The only new numbers are a per-loop marker: 4 vectors of 960, zero at start, about 0.01 % of the model. The E33 code already has it. An optional input re-injection (add the prelude state back each loop) needs no new weights.

One alternative to test as a second arm: loop all three upper layers (read + both local layers) and use only the head as the answer layer. More thinking per loop, but no untied answer layer. The literature (Mixture-of-Recursions, Huginn) favours keeping the first and last layers untied.

The hard part: turning "found B" into "ask about B"

Read 1 returns the value of the latent "A → B". It carries B as a target. Read 2 must match the key of "B → C", which carries B as a source. Nothing forces these two forms of B to line up.

End-to-end Memory Networks met the same problem and solved it by tying weights: the output embedding of hop k is the input embedding of hop k+1, so what a read returns is already in the form the next query needs. In your design, the local layer inside the loop is where that conversion is learned: attention over the question side plus a feed-forward turn "target B" into "query for source B". E33 had only one feed-forward between reads for this job.

Two traps to watch in the attention logs

Backward-edge echo. A query for "B" can match both "B → C" (B as source, correct) and "A → B" (B as target, already used). Each latent holds both ends of its fact. The page encoder sees the order inside a fact block (marker, source, target), so the key can keep source and target in separate directions, but training has to find this. Log, per loop, which latent gets the most attention. A model stuck on the echo will re-read "A → B".

One shared key head. The memory has one 64-d key per latent, shared by 15 query heads. Different heads can read different directions of that key (one head for "source = B", one for "already visited"), but 64 dimensions is tight. If the logs show echo, the fix is 2 key/value heads (a parameter change, so a later step).

Measured (4 Oct): neither trap was reached. The read never addressed even the first link, so there was no "found B" to turn into a query, and no echo to fall into. Both traps become the things to watch once the one-hop stage works.

Old 4 · How the gradients flow

Switch the diagram in section 1 to "backward" to see the same paths on the network. The loss is a weighted sum over the loop exits. Every exit's gradient enters the network at its own loop, so loop 1 is never more than one core-step from a loss signal. That is the "deep supervision" that the HRM/TRM analysis found to be the real driver.

Tied core
The core's weights receive the sum of the gradients from all 4 loops, as in backpropagation through time. Four loops is short, so full backprop is fine. Huginn truncates only beyond 8 loops.
Into the memory
Each loop's read sends gradient into the memory keys and values, which flow back into the writer: 4 contributions per fact. With "writer frozen" this path stops, so the notebook stays exactly as today and retrieval cannot degrade.
Detach between loops
A TRM-style option: stop gradients between loops, so each loop learns "one good step from any state". Cheaper and more stable, but no credit flows from loop 3's error back to loop 1's query. Test it as an arm, not as the default.

Analogies, checked

  • Student and notebook. The notebook (memory) is written while reading the book and does not change during the exam. The student's working thoughts (the residual state) do. Rereading the notebook with a sharper question is exactly the loop. The analogy holds.
  • Working memory vs long-term memory. Psychology calls it cue-dependent recall: what you retrieve depends on the cue, and each retrieval gives a better cue. The residual stream is working memory (small, changing). The latents are episodic memory (large, fixed).
  • Where the analogy breaks. A student "notices" what is missing. A static 4-loop model does not decide anything: it always takes 4 looks. Noticing needs a stopping head (Ouro's exit gate), which is the dynamic version for later.

Depth loop vs latent thoughts (the earlier proposal)

  • Both give one dependent memory read per hop. The theory says T loops can simulate T chain-of-thought steps (Saunshi 2025).
  • The loop is simpler: no new positions, no sequential generation in training (the 4 loops unroll in one pass), and the existing E33 code nearly does it.
  • Thoughts are more flexible: each thought is a new position that later steps can attend to, and the hop count is not capped by R.
  • Recommendation: build the loop first (your version). Keep latent thoughts as the next arm if the loop stalls on more hops than loops.
