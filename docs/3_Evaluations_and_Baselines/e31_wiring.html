E31 wiring: every layer, every token, on a 17-token example

Yes, there are two paths running in parallel from the same token embeddings. The memory path (purple, below the embeddings) writes latents from each window of the book. The main path (blue, above) is an ordinary causal language model over the whole row. They meet at one place: the global-read layer, where the memory slots are appended to that layer's keys and values. There is no separate "decoding stage". The answer is produced by the main path's top layers, like any next-token prediction. Companion page: E31 architecture & checklist.

Update, 1 Oct 2026: the best version. The page now starts on the configuration that won the E30 vs E31 study. It uses the page-encoder writer, one reader entry per latent (32 per window, about one per 6 tokens), the length-invariant address with the order code, and the windowed global read. E30 is parked. The new section "Where latent reasoning could live" below maps the candidate places for multi-hop reasoning onto this wiring.
Update, 27 Sep 2026. The wiring below is what was built and trained. Two options were added for long inputs; both are toggles here:
  • Windowed global read. In the global layer, book-side tokens read only the last 4 book states here (256 at scale), not the whole book. The memory becomes the only long path and cost is linear. Click a book-side global-read state to see its narrower dependencies.
  • Length-invariant address. Each slot's key is rotated at the QUERY position instead of where it read, and carries no window-start position. The reader sees the same geometry at any book length. Trained on books of at most 16k, it holds 80–81 % at 128k; the original address reaches only ≈ 2× its training length.

How to use this page

  1. Click any state (a cell). Orange shows everything it depends on, all the way down to token embeddings, and lines show its direct inputs.
  2. Start with the answer prediction at position 13 (green, top row). Its dependencies run through the global read into the memory slots, then down to the fact's tokens. That's the whole route the fact takes.
  3. Switch Writer → E30 as built and click the slot row: the writer reads the main path's first local layer, where value letter v3 can't see the keymark (no ●).
  4. Switch Setting → text: no QUERY, every position predicts the next token and reads the slots of windows that have already closed, so nothing is a dead end.
  5. Step through the forward pass to see the order in which layers compute.

Where latent reasoning could live in this network

Today the question side gets one look at the memory: one global-read layer, then two local layers that only turn what was fetched into letters. Following a chain A → B → C → D stored in different windows needs a second look whose question depends on what the first look returned. The diagram marks every place such a dependence could be added. Hover a number for details. The literature review behind the "evidence" column: latent reasoning review (1 Oct).

Why the read loop (③) most likely failed. These hypotheses come from the literature and have not been tested here.
  1. The returned value is not a usable question. The first read returns B as a value, the content of the slot "A → B". The second hop needs B as a key, to match the slot "B → C". Nothing trains those two forms to line up. DiscoLoop and the identity-bridge papers find the bridge entity decodable but not aligned with its input embedding. Feeding back a discrete embedding of the bridge fixes it.
  2. The memory never computes. Every multi-hop success over a memory in the review either loops over the memory itself (Sleep, ImReasoner, loop+memory) or appends thoughts as new inputs (Coconut, superposition). Our slots are frozen per window.
  3. Signal and budget. Coconut without its curriculum is no better than no chain of thought. Composition is learned late (grokking, about 50× the steps needed to fit). Graph search becomes learnable only with balanced hop counts.
