1 · How to pick sharper?
Give the writer context first
Today the writer sees only 16 tokens, so it can't tell a fact from filler. Then add competition between the learned questions, per-channel picks, and a direct training signal for picking.
2 · What limits bandwidth?
What the writer can recognise, not size
Raw note capacity ≈ 330 kbit. A perfect picker could carry ≈ 320 bit. The 16-token receptive field allows ≈ 26 bit. Measured: 25.7 bit.
3 · Are the notes a memory?
Yes: a write-once episodic memory
Improve the write by binding (key+value into one entry), competition, and an associative matrix per page. Reason at read time in 2–4 question-driven hops.
4 · Can it stream?
Yes, and it's a natural fit
The page write is already local. Add a small state carried across pages, an append-only multi-level archive, and questions at random points during training.

1 · Bandwidth: where the wall actually is

I start with bandwidth because it explains the picking problem. Measured case: the 1024-token "lookup" exam, 31M model, sliding-window notes (160 notes, 1 KV head of 64 dims).

What that exam actually tests. The book is 1024 random DNA letters with one planted fact: keymark · 2-letter key · 32-letter value. The answer is the 32-letter value (64 bits). So the "lookup" is really "find the marked spot and copy 32 random letters through the notes." It's a bandwidth test, not an addressing test.

The receptive-field wall: what the writer can see

The notes are written from token states after one local layer that looks 16 tokens back (mask q − kv < 16). A value letter can "know" it belongs to the fact only if the keymark is within its 16-token view. That holds for letters 1–13 (green). Letters 14–32 look exactly like random filler (grey), so no fixed learned question can single them out. The prediction is 13 letters × 2 bits = 26 bits.

The measured plateau hits the prediction

Five runs (lengths 1024 and 2048, page sizes 128 and 256, widths 31M and 50M, lookup and lookalike exams) all stop at 24–26 bits. A compression wall would move with length and page size; this one doesn't. At 512 tokens the claim runs placed the fact at a fixed position (right-aligned), so position alone found it and the model recovered the full 48 bits.

The bandwidth ladder (1024-token lookup)

Each rung is a stricter limit. The binding one is salience: what the writer can recognise as worth keeping. Raw size is 10,000× away from mattering.

2 · Making the key–query pick sharper, and making the gradient reach it

Why the write learns slowly: two softmaxes in a chain

∂L/∂sj,t = αj · wj,t · ⟨ g , vt − v̄j ⟩     (s = write score of token t in note j, α = reader's weight on note j, w = note's weight on token t, g = loss gradient at the reader output)

At the start α ≈ 1/C and w ≈ 1/W, so a token's pick gets ≈ 1/(C·W) of the signal. The reader can't favour a note until the writer makes it useful, and the writer gets no signal until the reader favours it. This chicken-and-egg problem shows up in the ledger as late takeoff, rank collapse at high step size, and dead 512-token pages. Wider pages make w smaller, and softmax peaks fade as W grows (SSMax, "Softmax is not enough").

Design principle: keep the write question-blind but well-informed (context + competition + per-channel picks), and put the real pickiness in the read, where the question exists: an indexer scores pages and fetches their contents, trained by score-weighted fusion and a teacher KL. The literature is unanimous that every learned selector conditions on a query. None makes static questions "picky" by themselves.

3 · Treating the notes as memory: better writes, and where reasoning lives

Yes, they are a memory: content-addressed (the note key is the address), write-once, read-many, one store per page. What's missing compared with a real memory: binding (key and value in one entry), allocation (every salient item gets a slot), overwrite (a new value for the same key replaces the old one), and multiple reads.

4 · Streaming: encode as tokens arrive, answer any time

Why E30 is already half-way there

1
A page's notes depend only on that page, so they can be written the moment the page closes. Cost is O(W·K) per page, constant per token.
2
The exclusive mask already enforces "after the question, only notes". That is the streaming contract.
3
The row format already counts multiple QUERY boundaries ("sides"), so rows with questions at random points are almost free. Fix the pooling leak first: with many questions, receiver-only pages appear and the leak fires.

What streaming adds

A
A carried state across pages (a small delta-rule matrix, ARMT-style, O(1)). The writer then knows "this key appeared before" and has context beyond 16 tokens.
B
A multi-level archive: page notes kept append-only (like DeepSeek HCA), merged on a log schedule (log-linear attention, Fenwick tree) into chapter and volume notes. Raw text stays on disk for fetching (InfLLM / EM-LLM pattern).
C
Training: segments with truncated backprop through time, curriculum on segment count (RMT 1M paper), questions sampled at random times, BABILong-style evaluation at arbitrary points.

Two streaming families: fixed state vs growing archive

Fixed-state models (Mamba, DeltaNet, RMT) are cheap and extrapolate far, but lose recall once facts outnumber the state (a 750M gated DeltaNet falls to 13.8% on a two-needle test at 8K). Every production 1M system keeps some state that grows with N and searches it. The blueprint uses both: a small carried state for context, plus a growing, searchable archive for recall.
